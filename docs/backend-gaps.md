# Backend gaps

Gaps between the frontend requirements and `openapi.yaml`. No endpoints are invented; each gap needs a backend decision before the matching adapter is replaced. Affected code is marked `TODO(backend)`.

1. **Authentication (resolved)**: The backend now exposes register, login, refresh, logout, and current-user endpoints. The frontend defaults to `AUTH_PROVIDER=real`, posts email and password to `/api/v1/auth/login`, and keeps the access and refresh tokens in separate httpOnly cookies. `/auth/refresh` rotates the refresh token and restores the requested path after an expired access token. The frontend reads the backend claims `user_id`, `email`, `roles`, and `exp` for routing, while signature and expiry enforcement remain on the backend. `AUTH_PROVIDER=mock` is retained only for UI development and cannot call authenticated backend endpoints.
2. **Public provider list and profile**: Only `GET /api/v1/services` is public. There is no public provider list or provider detail endpoint. Cards are built per service, so a provider with several services appears several times.
3. **Provider card fields**: Public service items include `provider_display_name` from the provider profile. They do not include neighborhood, city, photo, rating, or review count. The frontend displays only the provider display name, service name, category, price, and verified status; unsupported location, photo, rating, and review UI was removed rather than populated with placeholders.
4. **Service filters**: `GET /api/v1/services` accepts `cursor`, `limit`, and the beauty-service `category`. Category values are mirrored from `api/openapi.yaml` in `src/config/messages.fa.ts` and remain hard-coded until a taxonomy endpoint exists. The home page applies the search query to the fetched page in memory (`src/lib/listing/filters.ts`). City and neighborhood filters were removed because the backend has no address data; search remains incomplete across pages until the endpoint supports a query parameter.
5. **Zarinpal callback return (resolved)**: The backend callback now verifies server-to-server and redirects the browser with `303 See Other` to the configured `PAYMENT_RETURN_URL`, which points at `/wallet/payment/result`. The redirect contains no payment ID, authority, token, or return path. The frontend reads its short-lived httpOnly payment ID and validated return-path cookies and displays only the state from authenticated `GET /api/v1/payments/{paymentID}`. `PAYMENT_RETURN_FORWARD_TO_BACKEND=true` remains available for deployments that configure Zarinpal to call the frontend result page directly; it defaults to false.
6. **Admin provider list (resolved)**: Admins can list providers through `GET /api/v1/admin/providers` with cursor pagination, a verification-status filter, and text search. The frontend uses the endpoint and blocks approvals for incomplete profiles.
7. **Image upload**: Provider photos have no upload or media endpoint.
8. **Error code catalog**: Problem `code` values are not documented. Persian messages are mapped by HTTP status only (`src/lib/api/problem.ts`). Code-specific messages should be added once the catalog exists.
9. **Other services of a provider**: The public API has no endpoint that lists a provider's services, so the service detail page cannot show "other services" from the same provider. The section is omitted rather than faked (`src/app/services/[id]/page.tsx`). Item 2 also applies here.
10. **Provider time zone before availability**: `AvailabilityResponse.time_zone` is the only place the provider's zone is exposed, and it arrives only after the day's availability is requested. The booking page needs "today" in the provider's zone to build the date strip and validate `?date=`, so it uses `DEFAULT_PROVIDER_TIME_ZONE` (`src/config/booking.ts`, `Asia/Tehran`). Providers in other zones may see the wrong "today" until the zone is exposed on the service or provider.
11. **Booking time zone**: `Booking` has `starts_at` and `ends_at` in RFC 3339 but no provider time zone. The confirmation and success pages format times with `DEFAULT_PROVIDER_TIME_ZONE`, so they can show the wrong local time for providers in other zones. The confirmation page takes the zone from a fresh availability response instead.
12. **Booking conflict causes**: `POST /api/v1/bookings` returns 409 for a taken slot and for insufficient balance, and the error code catalog is undocumented (item 8). The action attributes a 409 by comparing `GET /api/v1/wallet` `available_irr` with the service price (`src/lib/booking/actions.ts`). A concurrent change can still be misattributed.
13. **Wallet top-up page (resolved)**: The confirmation page now links to `/wallet/charge?next=`. The charge page starts `POST /api/v1/payments/zarinpal`, stores a short-lived, validated return path, and the payment result page links back to the booking. The browser return after Zarinpal still depends on the callback agreement in item 5.
14. **Customer booking filters and time zone**: `GET /api/v1/bookings` supports only `cursor` and `limit`, so the customer dashboard applies a selected status filter to the fetched page in the server component; a backend status filter is needed to filter all bookings consistently across pages. `Booking` also omits the provider time zone, so dashboard details use `DEFAULT_PROVIDER_TIME_ZONE` (currently `Asia/Tehran`) until the API exposes it. Wallet transactions do not define a booking-reference format or per-booking settlement/refund breakdown, so the dashboard does not infer refund or settlement details.
15. **Cancellation eligibility details**: The cancellation endpoint returns 409 for a booking outside its configured cancellation window or in an invalid state, but the contract does not expose the cutoff or precise rejection reason. The dashboard offers cancellation for confirmed bookings and shows a general localized 409 message.
16. **Overnight working-hour precision**: `WorkingInterval.closes_at` is limited to `23:59`, with no representation for `24:00`. The editor splits overnight ranges at `23:59` and `00:00`, which cannot represent the final minute exactly. Extend the contract to allow `24:00` as an exclusive close time to preserve the full requested range.
