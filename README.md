# Beautyra

Persian RTL beauty and personal-care appointment-booking frontend built with Next.js App Router, TypeScript, and Tailwind CSS. All backend requests run on the server; the session JWT is stored in an httpOnly cookie and is never passed to browser JavaScript.

## Setup

Requirements: Node.js 22 and npm.

```bash
npm ci
cp .env.example .env.local
npm run dev
```

Set `API_BASE_URL` and `SITE_URL` to the deployment's backend and frontend origins. `AUTH_PROVIDER=real` is the default: registration uses `POST /api/v1/auth/register` (which creates a `client` account and then redirects to login), and login uses `POST /api/v1/auth/login` with email and password. Access and refresh tokens are stored in separate httpOnly cookies; `/auth/refresh` rotates the refresh token before redirecting back to the protected page. `/account` reads the authenticated profile from `GET /api/v1/me`. `AUTH_PROVIDER=mock` remains available for UI-only development, but its unsigned tokens are rejected by the backend, so protected API calls require `real`. Do not use mock authentication in production. `USE_MOCK_META=true` enables placeholder provider card details until the API exposes those fields.

## Commands

```bash
npm run dev

npm test

```

The app is served on port 3000 by default. `npm run gen:api` regenerates API types from `openapi.yaml`.

## Architecture

- `src/app` contains App Router pages and metadata routes.
- `src/components` contains accessible server-rendered UI and small client components for forms and interactions.
- `src/lib/api` owns server-side contract calls, problem responses, and generated schema types. Authenticated calls read the JWT from the httpOnly cookie and use `no-store` for user-specific data.
- `src/lib/auth` owns session handling, role guards, and the development/real auth adapters.
- `src/config/messages.fa.ts` centralizes Persian interface copy. `src/lib/format` and `src/lib/jalali` centralize Persian digits, money, and Jalali date presentation.
- `docs/rendering-strategy.md` describes caching and rendering choices; `docs/backend-gaps.md` tracks missing API contract capabilities.

## Rendering and security

Public service listings/details use tagged server-side caching and are invalidated when a provider's verification changes. Wallet, bookings, availability, and admin actions are dynamic and are not cached. Client Components are limited to interactive forms and controls. `next.config.ts` applies a Content Security Policy and security headers and restricts optimized remote images to the configured API host. Admin Server Actions require an admin session, validate form boundaries, and apply a process-local request limit. The process-local limiter is a lightweight abuse guard, not a distributed rate-limiting service.

## Admin pages

- `/admin/providers` accepts a provider ID and verification status because the API has no admin provider-list route. Updates use `PATCH /api/v1/admin/providers/{providerID}/verification` and invalidate the public `services` cache tag.
- `/admin/refunds` accepts a booking ID, sends an `Idempotency-Key`, and presents Persian status/error messages for the documented response codes.

Both pages are role-protected and excluded from indexing. See `docs/backend-gaps.md` item 6 for the provider-list limitation.

## SEO

The public home and service details have Persian metadata and canonical URLs. `sitemap.xml` lists the public home and published services; `robots.txt` excludes account, provider, booking, wallet, and admin routes. The shared Open Graph image is generated by `src/app/opengraph-image.tsx`.

## Docker

Build and run a standalone production image:

```bash
docker build --build-arg API_BASE_URL=https://api.example.test --build-arg SITE_URL=https://beautyra.example.test -t beautyra .
docker run --env-file .env.local -p 3000:3000 beautyra
```

The Docker image uses Next.js standalone output. Supply runtime variables from a secure environment; do not commit `.env.local` or real credentials.

## Backend TODOs

The frontend does not invent missing endpoints. Tracked contract gaps in `docs/backend-gaps.md` include:

1. Authentication, refresh/logout, and documented JWT claims.
2. Public provider list/profile and verified provider details.
3. Provider card data (name, location, photo, rating, reviews) and image upload.
4. Server-side city, neighborhood, and search filtering plus city/neighborhood taxonomies; service categories are already supported by the API.
5. A documented payment-provider callback/return agreement.
6. Admin provider listing; verification is currently ID-driven.
7. A documented problem-code catalog.
8. Listing other services for a provider.
9. Provider time zone on public service/provider data and bookings.
10. Distinguishing booking conflicts from insufficient wallet funds.
11. Server-side booking status filtering across cursor pages.
12. Exact cancellation eligibility/cutoff details.
13. `24:00` as an exclusive working-hours close time to represent overnight intervals precisely.

See `docs/backend-gaps.md` for current adapter behavior and relevant source files.
